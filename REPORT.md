# Звіт: аудит продуктивності "Каталогу репетиторів"

## Умови вимірювання

| | |
|---|---|
| Ноутбук | HP Laptop 15s-eq2xxx, AMD Ryzen 5 5500U (6 ядер, 12 потоків), 8 ГБ RAM, Windows 11 Pro 10.0.26200. Працював від мережі, схема живлення "Збалансований" |
| Браузер | Google Chrome 157.0.8103.78 у headless-режимі через Puppeteer 25. Кожен запуск у чистому профілі без розширень, в окремому incognito-контексті |
| Збірка | production: `npm run build` і `npm run preview` (http://localhost:4173) |
| Завантаження | CPU throttling 4x, мережа Fast 4G (165 мс затримки, приблизно 8 Мбіт/с), кеш вимкнений, вікно 1366x768 |
| Взаємодії | CPU throttling 4x, мережа без обмежень, вікно 1366x768 |
| Lighthouse | версія 13.6, режим Navigation, Desktop, throttling через DevTools (для Desktop це мережа без обмежень і CPU 1x) |
| Повтори | кожен сценарій 5 разів, у таблицях медіана. Усі окремі запуски є в `report/data/*.json` |

Заміри я робила скриптом [perf/measure.mjs](perf/measure.mjs) (`npm run perf -- назва`), а не руками.
Так кожен запуск однаковий: ті самі кліки в тих самих місцях і ті самі паузи. Тривалість взаємодії
рахую так само, як рахується INP. Через Event Timing API беру всі події з однаковим `interactionId`
і дивлюся на найдовшу, тобто час від натискання до наступного кадру. Long tasks збираю через
`PerformanceObserver('longtask')`, а CLS рахую за тим самим правилом "вікон сесії", що й бібліотека web-vitals.

Трейси записуються в окремому шостому запуску, і в медіану він не йде, бо сам запис трейсу
навантажує процесор. Трейси лежать у `report/traces/`, їх можна відкрити в DevTools на вкладці
Performance кнопкою "Load profile".

Для кожного виправлення я міряю версії "до" і "після" по черзі в одному сеансі: запуск старої
версії, запуск нової, знову стара і так далі (`npm run perf -- назва --before адреса_старої_збірки`).
Спершу я міряла їх окремо, з різницею в годину, і на першому ж виправленні це мене підвело.
Нова версія здавалась на 10% повільнішою в пошуку, хоча коли я поміряла обидві версії впереміш,
різниці не було взагалі. Ноутбук після кількох годин під навантаженням працює то трохи швидше,
то трохи повільніше, і ця різниця між сеансами доходить до 10-15%. Коли версії чергуються,
цей дрейф однаково впливає на обидві.

Чому саме такі умови:
- CPU 4x, бо мій ноутбук набагато швидший за середній телефон чи старий ноутбук, і без сповільнення частину проблем просто не видно.
- Fast 4G тільки для завантаження. На localhost мережа миттєва, і 22 МБ картинок там нічого не коштують. Для взаємодій мережа не потрібна, тому там я її не обмежувала, щоб не було зайвого шуму.
- Lighthouse без simulated throttling. У simulated-режимі CLS береться з прогону без обмежень, а з localhost картинки іноді встигають прийти ще до першого кадру. Через це Lighthouse показував CLS 0, хоча зсуви на сторінці є.

використовую для TBT і для аудитів, наприклад "Image elements do not have explicit width and height".

## Що знайшла (Завдання 2)

Спочатку я дивилась Performance-трейси кожного сценарію: які задачі на Main червоні і що всередині.
Потім зняла CPU-профіль з назвами функцій (`npm run perf:profile`), це те саме, що вкладки Bottom-Up
і Call Tree, тільки одразу числами. Для обраних ще дивилась React Profiler у dev-режимі, щоб побачити,
які компоненти перемальовуються. Усі цифри нижче з базової лінії при CPU 4x. Total означає час
функції разом з усім, що вона викликає.

### 1. useBioClamp постійно змушує браузер перераховувати layout

Гіпотеза: прокрутка гальмує через хук, який на кожну подію `scroll` міряє тексти карток.

Що показав трейс: за час прокрутки браузер 202 рази рахував Layout, і 193 з них викликав JavaScript.
DevTools позначає такі місця червоним трикутником "Forced reflow", а над ними видно функцію `update`
з `useBioClamp.js`. Разом це 12,7 с layout за 26 с прокрутки. У профілі `update` займає 9,3 с на прокрутці
і 6,2 с на завантаженні. Крім того, хук перезапускається після кожного рендеру, тому ці перерахунки
є і в кліках, і в пошуку.

### 2. Сортування "Рекомендовані" рахує бал прямо в компараторі

Гіпотеза: кожна дія користувача пересортовує список, і саме сортування дороге.

Що показав профіль: `getVisibleTutors` займає 2,5 с на завантаженні і приблизно 1,2 с на кожен клік по ♡.
Майже весь цей час іде у `weightedRating`. На кліках V8 вбудовує її в компаратор `recommended`, тому
в Bottom-Up цей час записаний на `recommended`. Тест показав 13 046 викликів `tutorScore` для 200 репетиторів
за кілька рендерів.

### 3. formatPrice щоразу створює новий Intl.NumberFormat

Гіпотеза: форматування ціни дороге, бо форматер створюється заново для кожної картки.

Що показав профіль: на завантаженні `formatPrice` займає 1,3 с. Це 4000 викликів (2000 карток і 2 рендери),
приблизно 0,33 мс кожен. На кліках V8 вбудовує її в `TutorCard`, тому там росте власний час `TutorCard`:
1,5 с на три кліки.

### 4. Будь-яка зміна стану перемальовує всі 2000 карток

Гіпотеза: клік по ♡ в одній картці змушує React рендерити весь список.

Що показав React Profiler: після кліку в коміті рендеряться всі `TutorCard`. Колбеки створюються заново
при кожному рендері (`() => onSelect(tutor.id)`), `TutorCard` не обгорнута в `memo`, а `getVisibleTutors`
перераховується, хоча ні запит, ні фільтри не змінились.

### 5. У картинок немає розмірів, тому сторінка стрибає

Гіпотеза: CLS 0,482 дають фото, які до завантаження мають висоту 0.

Що показав трейс: є один великий Layout Shift на 0,482, приблизно через пів секунди після першого кадру.
Саме тоді приходять перші байти картинок, і браузер дізнається їхні розміри. До цього місця під фото
і банер не було, тому все, що нижче, з'їжджає вниз. Lighthouse теж показує аудит "Image elements
do not have explicit width and height", а зсунутий елемент у нього `main.layout`.

### 6. 22 МБ картинок, які вантажаться всі одразу

Гіпотеза: LCP 20 с складається з двох частин. Спочатку головний потік зайнятий рендером, а потім банер
довго вантажиться, бо ділить канал з усіма фото.

Що показав трейс: на сторінці 37 PNG. Фото мають розмір 900x900 і важать приблизно по 590 КБ, хоча в картці
вони шириною десь 320 px. Банер 2400x900 важить 1,3 МБ. Жодне фото не має `loading="lazy"`, тому браузер
качає всі 36 фото відразу, хоча на екрані видно 3-6 карток. Запити на картинки стартують тільки на 10,7 с,
бо поки не закінчилась довга задача рендеру, браузер про них просто не знає. Усі вони йдуть з пріоритетом Low.
Банеру потім піднімається пріоритет до High, але довантажується він тільки на 21,6 с, а останнє фото на 33,9 с.
LCP якраз і є моментом, коли намальовано банер.

Ще одне помітне місце це розмір DOM, бо на сторінці 2000 карток. У трейсі завантаження перший Layout
сторінки триває 4,3 с. Я до нього повернусь після основних виправлень, коли буде видно, скільки він
займає сам по собі.

## Виправлення (Завдання 3)

Цифри "до" і "після" для кожного виправлення я знімала в одному сеансі, по черзі: запуск старої версії,
запуск нової і так далі, по 5 запусків кожної, у таблицях медіана. Тому "до" тут може трохи відрізнятися
від базової лінії, яку я міряла раніше.

### Виправлення 1. useBioClamp

Найбільше тут гальмувала прокрутка, тому міряла насамперед її. Але переміряла й інші сценарії, бо цей хук
запускався після кожного рендеру.

Чому гальмувало. Хук перевіряє, чи вміщується опис репетитора в три рядки, щоб показати кнопку "Читати далі".
Робив він це на кожен scroll: у кожної видимої картки прибирав клас з обрізанням, дивився висоту тексту,
повертав клас і дивився висоту ще раз. А щоб віддати висоту одразу після зміни класу, браузер мусить тут же
заново розкласти всю сторінку з 2000 карток, і так по кілька разів на одну подію прокрутки.

Що я зробила. Тепер хук нічого не змінює, щоб поміряти текст: якщо текст обрізаний, його `scrollHeight` більший
за `clientHeight`, і цього досить. Спочатку я читаю розміри всіх потрібних карток, а вже потім ставлю позначки,
тому браузер рахує layout один раз. Обробник `scroll` я прибрала зовсім і поставила `IntersectionObserver`.
Він сам каже, коли картка наближається до екрана, причому заздалегідь, за висоту екрана до появи
(`rootMargin: '100% 0px'`). Картки, які видно одразу після рендеру, міряю ще до першого кадру, щоб кнопка
не вискакувала із запізненням. Код у [src/hooks/useBioClamp.js](src/hooks/useBioClamp.js).

По дорозі довелося змінити ще одну річ. Раніше хук додавав картці клас `has-more`, а React, коли картку вибирають,
повністю переписує її `className`, і цей клас пропадав би. Раніше цього не було видно, бо хук перезапускався після
кожного рендеру і ставив клас знову. Тепер позначка зроблена атрибутом `data-has-more`, його React не чіпає,
а в [src/styles/index.css](src/styles/index.css) я поміняла один селектор.

Щоб переконатися, що нічого не зламалось, я відкрила стару і нову версії поруч і подивилась, на яких картках
є "Читати далі": у кількох місцях списку, після того як відкрила і закрила картку, і коли звузила вікно.
Скрізь було однаково. Тести теж проходять.

Цифри (сирі дані в [report/data/1-bioclamp.json](report/data/1-bioclamp.json)):

| Сценарій | Метрика | До | Після | Зміна |
|---|---|---|---|---|
| Прокрутка | сума long tasks за 20 прокручувань | 20,5 с | 12,4 с | -39% |
| | найдовша задача | 1,84 с | 1,39 с | -25% |
| Обрані | медіана кліку | 2552 мс | 2156 мс | -16% |
| Картка | відкриття | 2352 мс | 2072 мс | -12% |
| | закриття | 2176 мс | 1912 мс | -12% |
| Завантаження | LCP | 19,9 с | 17,6 с | -11% |
| | сума long tasks | 10,7 с | 9,8 с | -8% |
| Пошук | медіана натискання | 712 мс | 712 мс | без змін |

У трейсі прокрутки (`report/traces/1-bioclamp-scroll-before.json` і `1-bioclamp-scroll.json`) різницю видно одразу.
До виправлення DevTools показував 387 попереджень "Forced reflow", після нього жодного. Layout раніше рахувався
202 рази, і 192 рази його викликав наш код, а тепер 27 разів і жодного разу з JavaScript. На layout ішло 9,3 с,
стало 1,4 с, а JavaScript у довгих задачах скоротився з 10,1 с до 0,4 с.

На пошук виправлення не вплинуло. Спочатку я здивувалась, а потім зрозуміла: коли вводиш текст, перший ряд карток
ще нижче краю екрана, тож стара версія тут майже нічого не міряла. У пошуку час забирає сортування, це наступне
виправлення.

Довгі задачі під час прокрутки трохи лишились, тільки тепер у них немає нашого коду, там Commit і PrePaint
(9,2 с і 6,6 с). Це вже браузер малює сторінку з 2000 карток, тобто проблема розміру DOM.

Спершу я зробила інший варіант, без `IntersectionObserver`: залишила обробник `scroll`, але запускала перевірку
не частіше одного разу на кадр через `requestAnimationFrame`, а видимі картки шукала бінарним пошуком. Потім
поміряла обидва варіанти і оригінал по черзі, два кола по 3 запуски (у таблиці середнє двох медіан):

| | Оригінал | IntersectionObserver | scroll + бінарний пошук |
|---|---|---|---|
| прокрутка, long tasks | 24,8 с | 12,4 с | 17,6 с |
| пошук, медіана натискання | 724 мс | 716 мс | 688 мс |

У пошуку різниця в межах шуму, а прокрутка з `IntersectionObserver` помітно швидша. Думаю, справа в тому, що він
міряє картку ще до того, як вона з'явиться на екрані. Коли в картці з'являється кнопка, картка стає вищою і вся
сітка під нею зсувається, а за межами екрана це обходиться браузеру дешевше. Тому я залишила `IntersectionObserver`.
